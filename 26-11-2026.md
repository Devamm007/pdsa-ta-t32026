## q1

### Problem Overview: Activity Selection (GeeksforGeeks)
Given two arrays `start` and `finish` of length `n`, where `start[i]` and `finish[i]` denote the start and finish times of the `i`-th activity, find the **maximum number of activities** that can be performed by a single person assuming they can work on only one activity at a time.

An activity can only be selected if its start time is **strictly greater** than the finish time of the previously selected activity (`s > last_finish`).

---

### How to Approach the Problem
*(Connected to interval scheduling in `rough_w7_greedy-algos.pdf`)*

#### Why Naive Greedy Strategies Fail
1. **Pick Shortest Duration First (`finish - start`)**:
   - A short activity placed awkwardly in the middle can overlap two longer, compatible activities.
   - Example: `(1, 5)`, `(4, 6)`, `(5, 9)` (with strict `s > last_finish`, or `(1, 6)`, `(5, 7)`, `(6, 10)`). Picking `(4, 6)` or `(5, 7)` blocks both neighbors, yielding `1` activity instead of `2`.
2. **Pick Earliest Start Time First (`start`)**:
   - An activity that starts earliest might run for a very long duration and block many shorter activities behind it.
   - Example: `(1, 100)`, `(2, 3)`, `(4, 5)` -> picking `(1, 100)` yields only `1` activity instead of `2`.

#### Optimal Approach: Greedy by Earliest Finish Time
1. **Core Intuition**:
   - Always pick the compatible activity that **finishes earliest**.
   - Finishing as early as possible leaves the **maximum remaining timeline** for subsequent activities.
   - By a greedy exchange argument, any optimal schedule's first activity can be swapped with the earliest-finishing activity without introducing any conflict.
2. **Algorithm Mechanics**:
   - **Guard Empty Input**: If `not start or not finish`, return `0`.
   - **Pair & Sort**: Combine `(start[i], finish[i])` using `zip(start, finish)` and sort by finish time (`key = lambda x: x[1]`). Pairing is essential so each start time moves along with its matching finish time.
   - **Sentinel Initialization**: Set `count = 0` and `last_finish = float('-inf')`. Using `-inf` avoids special-casing the first activity (even if start times are `0` or negative).
   - **Linear Greedy Scan**: For each `(s, f)` in `activities`, if `s > last_finish`, accept the activity (`count += 1`) and update `last_finish = f`.
3. **Important Teaching Point (`>` vs `>=`)**:
   - Here, `if s > last_finish:` enforces **strictly non-overlapping** boundaries (matching the GeeksforGeeks problem statement and `intervalschedule` in `rough_w7_greedy-algos.pdf`).
   - In half-open interval variants where a task starting at exact time `t` can immediately follow one ending at `t`, the condition becomes `s >= last_finish`.
4. **Walkthrough of Examples**:
   - **Standard Example**: `start = [1, 3, 0, 5, 8, 5]`, `finish = [2, 4, 6, 7, 9, 9]`
     - Sorted by finish time: `[(1, 2), (3, 4), (0, 6), (5, 7), (8, 9), (5, 9)]`
     - `(1, 2)`: `1 > -inf` -> Select (`count = 1`, `last_finish = 2`)
     - `(3, 4)`: `3 > 2` -> Select (`count = 2`, `last_finish = 4`)
     - `(0, 6)`: `0 > 4` False -> Skip
     - `(5, 7)`: `5 > 4` -> Select (`count = 3`, `last_finish = 7`)
     - `(8, 9)`: `8 > 7` -> Select (`count = 4`, `last_finish = 9`)
     - `(5, 9)`: `5 > 9` False -> Skip
     - **Result**: `4`
   - **Session Board Example (`rough_w7_greedy-algos.pdf`)**:
     - Pairs `(s, f)` sorted by finish time: `(1, 2), (1, 3), (3, 4), (1, 5), (4, 5), (5, 8), (7, 9), (11, 12), (10, 13)`
     - Notice `(4, 5)` is skipped after selecting `(3, 4)` because `4 > 4` is `False`.
     - Selected: `(1, 2) -> (3, 4) -> (5, 8) -> (11, 12)` -> **Result**: `4`.

---

### Python Code

```Python
class Solution:
    def activitySelection(self, start: list[int], finish: list[int]) -> int:
        #code here
        if not start or not finish:
            return 0
        activities = sorted(zip(start, finish), key = lambda x: x[1])
        
        count = 0
        last_finish = float('-inf')
        
        for s, f in activities:
            if s > last_finish:
                count += 1
                last_finish = f
                
        return count
```

### Complexity Analysis
- **Time Complexity**: O(n log n), where `n` is the number of activities.
  - Pairing via `zip` takes O(n), sorting by finish time takes O(n log n), and the greedy scan takes O(n).
- **Space Complexity**: O(n) to store the sorted list of `(start, finish)` tuples in `activities` (plus Timsort's O(n) auxiliary space).

## q2

### Problem Overview: Jump Game (LeetCode 55)
You are given an integer array `nums`. You start at index `0`, and each element `nums[i]` represents the **maximum jump length** you can make from index `i` (you can jump anywhere from `1` up to `nums[i]` steps forward).

Return `True` if you can reach the last index (`len(nums) - 1`), or `False` otherwise.

---

### How to Approach the Problem

#### Why the Initial Thinking Fails (Debugging Session Draft)
In the initial draft (`# Faulty Code, Just Started Thinking`), two issues caused the logic to break:
1. **Taking fixed full jumps (`curr = curr + nums[curr]`)**:
   - `nums[curr]` is the *maximum* allowed jump, not a mandatory step size.
   - Always jumping the full distance can land directly on a `0` and trap you, even when a shorter jump reaches a stronger index.
   - Example: `nums = [2, 3, 0, 1, 4]` -> jumping `2` steps from index `0` lands on index `2` (`nums[2] = 0`), whereas jumping `1` step to index `1` (`nums[1] = 3`) reaches index `4`.
2. **Incorrect jump indexing & bounds (`curr + nums[i]`)**:
   - The inner loop checked `curr + nums[i] >= target_idx`, which added the jump power from `i` onto `curr` instead of `i` (`i + nums[i]`), and could also jump `curr` out of array bounds (`IndexError`).

#### Optimal Approach: Greedy Reachability Frontier (`max_reach`)
1. **Core Intuition**:
   - Instead of trying to track *which specific sequence of jumps* gets us to the end (which branches exponentially), track only the **farthest index reachable so far** (`max_reach`).
   - Because any jump length from `0` up to `nums[i]` is valid, if index `i` is reachable, **every index in `[0, max_reach]` is reachable**.
2. **Step-by-Step Mechanics**:
   - Set `target_idx = len(nums) - 1` and `max_reach = 0`.
   - Iterate `for i, jump in enumerate(nums)`:
     1. **Unreachable Guard (`if i > max_reach: return False`)**: If the current index `i` exceeds `max_reach`, there is a gap (caused by earlier `0`s) that no previous index could clear. We can never reach `i` or anything after it -> return `False`.
     2. **Expand Frontier (`max_reach = max(max_reach, i + jump)`)**: From index `i`, we can reach up to `i + jump`.
     3. **Early Exit (`if max_reach >= target_idx: return True`)**: Once the frontier reaches or passes `target_idx`, the goal is guaranteed -> return `True` immediately.
   - Return `True` if the loop completes.
3. **Trace Walkthroughs**:
   - **Reachable Example**: `nums = [2, 3, 1, 1, 4]` (`target_idx = 4`)
     - `i = 0, jump = 2`: `0 <= 0` -> `max_reach = max(0, 0 + 2) = 2`
     - `i = 1, jump = 3`: `1 <= 2` -> `max_reach = max(2, 1 + 3) = 4 >= 4` -> returns `True` immediately!
   - **Unreachable Example (Session Trace: `3, 2, 1, 0, 4`)**: `target_idx = 4` (`mr` = `max_reach`, `tgi` = `target_idx`)
     - `i = 0, jump = 3`: `0 <= 0` -> `max_reach = max(0, 0 + 3) = 3`
     - `i = 1, jump = 2`: `1 <= 3` -> `max_reach = max(3, 1 + 2) = 3`
     - `i = 2, jump = 1`: `2 <= 3` -> `max_reach = max(3, 2 + 1) = 3`
     - `i = 3, jump = 0`: `3 <= 3` -> `max_reach = max(3, 3 + 0) = 3` (`mr = 3 < tgi = 4`)
     - `i = 4, jump = 4`: `4 > 3` (`i > max_reach`) -> returns `False`!
4. **Edge Cases**:
   - Single-element list `nums = [0]`: `target_idx = 0`; at `i = 0`, `max_reach = 0 >= 0`, returns `True`.
   - Zero at start with length > 1 (`nums = [0, 2, 3]`): at `i = 0`, `max_reach = 0`; at `i = 1`, `1 > 0`, returns `False`.

## q3

### Problem Overview: Validate Binary Search Tree (LeetCode 98)
Given the `root` of a binary tree, determine if it is a valid **Binary Search Tree (BST)**.

A valid BST must satisfy:
- The left subtree of a node contains only nodes with keys **strictly less than** the node's key (`< node.val`).
- The right subtree of a node contains only nodes with keys **strictly greater than** the node's key (`> node.val`).
- Both the left and right subtrees must also be valid BSTs.

---

### How to Approach the Problem
*(Connected to BST subtree bounds in `rough_w6_part-1.pdf` and BST traversals in `rough_w6-7_bst-traversal-&-avl-trees.pdf`)*

#### Critical Pitfall: Local Parent-Child Checks Are Insufficient
Checking only `node.left.val < node.val < node.right.val` at every node is **wrong**. Every ancestor imposes a global bound on all descendants in its subtree:
```
        5
       / \
      1   7
         / \
        3   8
```
- At node `5`: `1 < 5 < 7` (locally valid).
- At node `7`: `3 < 7 < 8` (locally valid).
- Yet this tree is **invalid**: node `3` sits in the **right subtree of `5`**, so `3` must satisfy `5 < 3 < 7`, which fails (`3 < 5`).
- Similarly, duplicate keys (e.g., `node.val == low` or `node.val == high`) violate strict BST ordering.

#### Approach: Top-Down DFS with Valid Range `(low, high)`
1. **Core Intuition**:
   - Pass down an allowable open interval `(low, high)` that every node in the current subtree must satisfy.
   - Start at `root` with `(-math.inf, math.inf)` (or `(float('-inf'), float('inf'))`), which accommodates any integer node value including 32-bit boundary values (`-2^31` to `2^31 - 1`).
2. **Recursive Bound Tightening**:
   - **Base Case**: If `not node`, an empty tree/subtree is a valid BST -> return `True`.
   - **Range Check**: Verify `low < node.val < high`. If violated (including equality for duplicates), immediately return `False`.
   - **Left Subtree**: All values must remain greater than `low`, and strictly less than `node.val`:
     `self.validate(node.left, low, node.val)`
   - **Right Subtree**: All values must be strictly greater than `node.val`, and remain less than `high`:
     `self.validate(node.right, node.val, high)`
3. **Trace Walkthrough on Invalid Tree (`[5, 1, 7, None, None, 3, 8]`)**:
   - `validate(5, -inf, inf)`: `-inf < 5 < inf` -> True
   - `validate(1, -inf, 5)`: `-inf < 1 < 5` -> True (children `None` return `True`)
   - `validate(7, 5, inf)`: `5 < 7 < inf` -> True
   - `validate(3, 5, 7)`: checks `5 < 3 < 7` -> **False!** Short-circuits and returns `False`.
4. **Alternative Note (In-Order Traversal)**:
   - As covered in `rough_w6-7_bst-traversal-&-avl-trees.pdf`, an **In-Order Traversal** (`Left -> Parent -> Right`) visits a valid BST in **strictly ascending order**. Tracking `prev` during an inorder traversal and checking `prev < node.val` is an equivalent O(n) approach.

---

### Python Code

```Python
# Definition for a binary tree node.
# class TreeNode:
#     def __init__(self, val=0, left=None, right=None):
#         self.val = val
#         self.left = left
#         self.right = right

import math

class Solution:
    def validate(self, node, low, high):
        if not node:
            return True
        if not (low < node.val < high):
            return False
        return self.validate(node.left, low, node.val) and self.validate(node.right, node.val, high)

    def isValidBST(self, root: TreeNode | None) -> bool:
        # return self.validate(root, float('-inf'), float('inf'))
        # OR
        return self.validate(root, -math.inf, math.inf)
```

### Complexity Analysis
- **Time Complexity**: O(n), where `n` is the number of nodes in the tree. Each node is visited at most once, with early exit if an invalid node is encountered.
- **Space Complexity**: O(h) auxiliary space for the recursion call stack, where `h` is the height of the tree:
  - **Balanced BST**: O(log n)
  - **Skewed Tree (Worst Case)**: O(n)
